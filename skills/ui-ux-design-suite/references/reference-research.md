# Reference Research

Reference research should reduce design uncertainty, not create a mood board for its own sake.

## What to search for

Search by **task/pattern**, not only by brand:

- complex table filtering and bulk actions;
- settings taxonomy;
- onboarding and empty states;
- resource monitoring;
- file browsing;
- permission/error recovery;
- search → filter → inspect → act workflows;
- mobile adaptation of dense desktop workflows.

## Evidence hierarchy

1. Current product behavior and user evidence.
2. Platform conventions and authoritative design guidance.
3. Mature products solving an analogous task.
4. Maintained open-source implementations/design systems.
5. Community discussions for lived pain points and workflow friction.

## For every selected reference

Record:

- exact pattern being referenced;
- user problem it solves;
- why it maps to this product;
- constraints that differ;
- what not to copy;
- whether the pattern is structural, interactional, or merely visual.

## Do not

- clone a fashionable product regardless of task;
- merge multiple incompatible design languages;
- use popularity as evidence that a pattern fits;
- copy a component without checking accessibility, license, maintenance, or integration cost when code reuse is involved.
