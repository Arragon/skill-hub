# Project plan audit

把 Linear 的交付承诺、仓库的实际实现和本地计划逐项对齐，输出有证据的进度判断与下一步任务。**已完成的保留，未完成的重新评估；实现、验证和正式 Gate 分别判断。**

## 确定范围

从当前请求和上下文确定仓库、Linear 项目、分支/里程碑范围，以及 PLAN.md 或指定计划文档的真实路径。缺少关键身份时先查找，仍无法唯一确定才询问；不要根据终端标题或工作目录名称推断仓库。

默认执行审计与建议。请求包含任务细化时生成执行任务；包含“更新/同步 Linear”时才写回。审计本身不授权产品修改、重开 Done、切换架构、发布或启动实现 agent。遵循当前会话已有授权，无须重复确认。重写完整架构或路线图只有在请求包含该工作时才做。

## 1. 建立可追溯基线

- 读取适用 AGENTS.md；跨模块判断时读取相关 `docs/architecture.md`、`docs/know-how.md`。检查实际实现、调用链、契约与测试，而不是只读取 README 和状态文件。
- 核实仓库根目录、remote、工作树、分支、HEAD、主线和未提交变化。分别说明成果处于未提交、分支实现、主线集成还是发布状态；远端未知就明确标注。不要为审计切换或重置用户工作树。
- 确认本地计划的路径、版本和适用范围。下载副本、仓库文件、Linear 文档可能不同；记录冲突，不静默选择一个覆盖另一个。
- 用当前可用的 Linear connector/API 读取项目、里程碑、关联计划、issue 详情、验收条件和依赖，遍历范围内所有分页。列出预期、已取得、已审计和遗漏的范围；分页未齐时不计算全项目完成率。不要把历史截图、搜索摘要或第一页当作完整项目。
- 历史记忆和 可用的历史检索工具 可以定位来源，但不能证明当前状态；需要历史材料时按其可用工具/技能读取，并回到仓库或源应用核实。连接受阻时继续可独立完成的本地审计，明确缺失来源和结论边界；不自行改凭据、代理或观察设置。

## 2. 按验收条件对账

将范围内每个 issue 映射到本地计划章节、验收条件、实现入口和验证证据。一个 issue 包含不同能力或 Gate 时拆为子行；不能用“某里程碑基本完成”替代逐项检查。没有明确验收条件的任务标记“需求待澄清”，不要自行发明完成标准。

每行分别填入：

| 维度 | 判断方式 |
| --- | --- |
| 实现 | 未实现 / 部分实现 / 原型 / 已接入；附分支、提交或工作区归属 |
| 验证 | 当前通过 / 当前失败 / 执行受阻 / 未运行 / 仅历史证据；注明覆盖范围 |
| Gate | 通过 / 未通过 / 待证据 / 不适用；独立列出前置依赖和外部验收 |
| 差距 | 实现缺口 / 验证缺口 / 计划漂移 / 架构不一致；可同时存在 |

检查正反两个方向：计划承诺是否落地，以及已有能力是否遗漏在计划中、被重复安排或仍标为未开始。文件存在、mock、stub、UI 壳和精确 ID 原型不能证明完整业务闭环。对 UI、真实账号、数据库、恢复、性能等，只按该任务要求核验对应层面的证据。

## 3. 判断证据是否适用

证据记录路径/行号或 issue/PR 链接、采集时间、提交、环境、场景和结果。实际运行结果优于自述，当前适用实现优于过期状态标签。最新报告也只有在场景、环境、阈值和版本适用时才支持当前判断。

保留历史失败和后续通过，解释比较条件；搜索性能通过不能消除账号运行、恢复或 UI 的证据缺口。HEAD 的通过报告也不自动覆盖未提交修改。旧原型与新的目标架构分别建立基线：评估可保留的契约、行为、测试和安全机制，不把旧原型完成率搬到新路线图，也不直接提出全量重写。

Done 与代码冲突时保留原状态和证据，在报告列出“Done 声明存在差异”及修复/复核建议。新的回归可建议独立任务；重开原票需要当前请求明确涵盖该操作。Gate 不能仅凭代码、本地测试或工程任务 Done 判定通过。

## 4. 执行与范围相称的验证

从 AGENTS.md、项目配置、锁文件及 CI 推导命令，报告实际使用的命令和结果。先运行能回答主要疑点的现有检查，是否扩大验证取决于共享契约和风险。

工具或依赖缺失时检查已存在且等价的运行入口；没有可确定入口就标记受阻。审计不要求安装依赖、启动生产服务或做迁移。临时配置/隔离环境必须说明与正式环境的差异；不能把替代检查宣称为正式验收。区分产品失败、测试契约失败和执行环境失败，无法归因时保持未知；不弱化测试或改变断言来制造通过。

## 5. 形成报告与可执行任务

按 [报告与任务格式](references/audit-output.md) 输出：先给真实进度判断和主要阻塞，再列来源/覆盖范围、逐项矩阵、验证结果以及按依赖排序的后续行动。长矩阵保存为 Markdown 并给出文件链接，聊天中保留结论和重点差距。

已完成工作简要保留；细化未完成和受阻项。任务包含输入、实现边界、依赖、正向/失败验收和证据交付，使指定能力级别的实现 agent 可以独立执行。技术选型或契约尚未确定时，先安排澄清/契约任务。把真实账号、人工体验、长期使用等外部验收单独标记，不能以模型自述代替。不编造负责人、日期、模型要求或完成百分比。

## 6. 请求包含 Linear 同步时

先生成具体变更表：issue、当前/目标状态、说明/验收条件变更、依据和依赖。只应用当前已授权范围；继续保留 Done 与已有证据，使用该工作区的实际状态定义。

本地成果尚缺验收时按实际流程使用 In Progress/In Review 或其等价状态。满足该票全部验收条件才建议/设置 Done；独立 Gate 按自身条件判断。更新说明和状态后读取回执核对；批量操作逐项记录成功/失败，创建结果不明时先查询再重试，避免重复任务。范围不含同步时只交付建议变更表，不执行写入。
