# 审计报告与任务格式

生成报告时读取本文件。按实际项目调整篇幅，保留能支撑判断的字段；没有的数据写明“未知/未取得”，不填虚构值。

## 报告结构

1. **交付判断**：当前可证明的能力、主要实现缺口、验证缺口与 Gate 阻塞。区分本地实现、主线集成和正式发布。
2. **基线与覆盖**：审计时间/时区；仓库路径与 remote；工作树/branch/HEAD/脏文件；远端核实情况；Linear 项目和筛选范围、分页完整性；本地计划路径与版本。列出取得、审计和遗漏的 issue；总数未知就不报完整完成率。
3. **逐项矩阵**：行粒度是一个可验证需求/验收条件，保留 Linear ID 与原状态。范围较大时按里程碑分组，附完整 Markdown，明确哪些仅抽查。

| Linear ID / 里程碑 / 原状态 | 本地计划章节 / 验收条件 | 实现与归属 | 验证状态 | Gate / 前置 | 证据 | 差距 / 下一步 |
| --- | --- | --- | --- | --- | --- | --- |

4. **证据与检查**：列出实际命令、结果、覆盖、失败/受阻原因。说明每个历史报告的版本和场景，哪些当前判断仍需重新验证；链接真实源文件/行号、artifact、PR/CI 或 issue。
5. **下一步**：先恢复可验证基线，再补契约/实现、集成和针对性验证，最后评审 Gate。具体顺序依项目依赖决定，独立可推进工作不必全部等待外部 Gate，但必须遵循项目实际边界。
6. **同步结果**（有请求时）：拟定或实际执行的 Linear 变更、readback 核对、失败与未写入项。明确区分“建议”“已写入”“已读回确认”。

## 任务交接字段

任务应是一个能够单独实现和验收的结果，不以文件数或固定小时数机械拆分。使用以下字段；条件不适用时说明理由。

- **关联**：原 issue、里程碑、本地计划章节、具体审计差距。
- **目标/输入**：触发场景、期望行为、输入契约与已有基线。
- **实现范围**：已核实的入口/模块、应保留的能力及边界；未确定的技术决策列为前置问题。
- **依赖**：契约、前置 issue、运行环境或外部证据。说明哪些仅阻止 Gate、哪些阻止实现。
- **验收**：可观察的正向结果、失败/边界场景和回归要求；阈值来自现有契约。不得只写“测试通过”“完善功能”。
- **验证/交付**：已确认的运行命令、需要新增的测试层、artifact/截图/日志、对应提交与结果。命令未确定时写清确认方式，不能假设命令存在。
- **状态/Gate**：满足什么条件可关闭工程任务，哪些条件仍需单独验收；外部人工/账号证据的采集者若未知就标为待指定。

若用户指定执行模型/能力级别，按其能力拆分契约、实现、失败场景和验收任务；不会因为历史项目曾使用某模型而给本项目强制相同模型。

## 判断示例

Linear 的 State 工程票处于 In Review，本地计划写“已完成”。列表与存储已在 feature 分支，来源跳转只有 stub；组件测试通过，但窄屏截图与真实数据库恢复证据未取得，发布 Gate 还要求长期真实账号使用。

应记录：实现部分接入、组件验证通过但仅覆盖已测部分、恢复与视觉验证待证据、发布 Gate 待外部验收、本地计划声明过宽。保留已经可证实的能力和原状态；分别安排来源跳转实现、恢复/视觉证据收集及外部 Gate 采集。不能用一个“State 完成”覆盖三种状态。
