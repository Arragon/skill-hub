# Product Razor

Use this reference only when the reviewed task is materially about product scope, roadmap, MVP, UX scope, feature planning, or product strategy.

These are domain heuristics, not universal laws.

## Scope Creep

Trace every major feature back to:

- a confirmed user need;
- a real workflow;
- a validated product requirement;
- a confirmed near-term roadmap item.

If a feature exists only because it "would make the product more complete", challenge it.

## Feature Inflation

A supporting feature can quietly become a product goal.

Ask:

> Does this feature directly improve the core workflow, or has the product started serving the feature?

If a supporting capability becomes the center of the roadmap without new evidence, re-check scope.

## Imagined Personas

Do not invent hypothetical users merely to justify features.

Examples:

- "Teams may need this."
- "Power users may want this."
- "Enterprise customers may require this."

Unless those users actually exist in the target or roadmap, treat the claim as unverified.

## Fake Future Requirements

Separate:

- current need;
- confirmed next need;
- plausible future;
- pure possibility.

A plausible future is not a current requirement.

## Premature Platformization

Challenge the pattern:

tool → configurable tool → extensible platform → ecosystem → marketplace

unless each transition is grounded in real demand.

If the user needs a tool, do not automatically design a platform.

## User-Scale Assumptions

Do not design for thousands of users when the product currently serves one or two unless there is explicit scale evidence or a confirmed roadmap.

Similarly, do not ignore real scale if it already exists.

## MVP vs Product Fantasy

MVP means the smallest version that solves the real problem well enough to use.

It does not mean:

- a fake demo;
- a non-persistent prototype;
- missing critical error handling;
- unusable UX;
- a knowingly broken core flow.

It also does not mean:

- all planned future features;
- generalized extension systems;
- full account ecosystems;
- speculative growth infrastructure.

## Roadmap Fiction

A roadmap item should have a reason.

Challenge roadmap entries that exist because:

- they were mentioned once in brainstorming;
- AI suggested them;
- they make the roadmap look complete;
- "we might need this later."

If no near-term trigger exists, `DEFER`.

## Product Success Test

For every retained feature, ask:

> If this feature did not exist, which real user outcome would fail?

If the answer is vague, challenge the feature.

## Product Decision Hierarchy

Prefer:

1. solve the core workflow;
2. remove friction in that workflow;
3. add necessary supporting capability;
4. preserve an obvious near-term path;
5. validate uncertain expansion;
6. only then broaden product scope.

Do not move downward without evidence.
