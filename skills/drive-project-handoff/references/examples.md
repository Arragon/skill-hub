# 行为示例

以下是合成场景，展示应产出的变化与回执；不宣称在真实 Drive 账户测试通过。

## 两次保存：增量、幂等、原文完整

已有：P1 的 INDEX → OVERVIEW、STATE、35 页完整接口规格 T1；D1 已批准 REST；STATE S7 显示登录实现中。

本次聊天最终结论：“登录实现完成，单元测试通过；端到端还没跑。下步检查移动端错误恢复。”实际证据为提交 C21、单测报告 E9；同一会话 `session_id=S-chat-14`。

第一次保存 `change_id=chg-P1-031`：
- 原样保留 T1 全文及图表，不用摘要覆盖
- STATE 中登录改为“实现与单元测试已验证，E2E 待验证”，引用 C21/E9；加入移动端恢复检查及其验收条件
- 更新 STATE 逻辑修订与 INDEX 对应条目；实际 store_revision 取工具返回值
- 写后重读确认，再回执“状态已保存；E2E 尚未验证”

紧接着说“再保存一次”，无新事实：读取当前状态后识别相同语义，不写文件、不创建另一个登录条目，不因新生成 change_id 重复内容。

随后跑出 E2E 失败 E10：这是第二个真实增量 `chg-P1-032`。只更新受影响测试状态/阻塞/下步，保留前面真实通过的单元测试和全部规格。不能把一次失败泛化为“全部测试失败”，也不能仍称“登录全部完成”。

## 较新提案不覆盖较早批准

昨日：项目负责人批准 D1“本期使用 REST，SDK 必须兼容旧客户端”。
今日：聊天“GraphQL 好像更灵活，先比较一下”。

保存：D1 仍 approved；另记 proposed 的比较任务，不改接口规格或验收标准。“最新聊天”限定当前项目、当前范围、最终立场，并不等于最后一句话具有批准权。

稍后负责人明确批准“下期改 GraphQL，本期继续 REST”：新增带“下期”范围的 D2，与 D1 并存。只有明确同范围替代才设置 supersedes。若来源身份或批准权无法确认，保留 proposed 并询问，不据此执行破坏性迁移。

## 并发、部分成功和超时

A 读取 STATE S7 准备保存单测结果；B 随后写出 S8，新增安全阻塞。A 提交前发现变化：
- 读完整 S8，保留安全阻塞，合并不冲突的单测结果
- 工具若有 revision 条件写：以 S8 的实际修订为前置条件；冲突时重新合并
- 工具只有无条件全文替换：不能靠“再读一次然后立刻写”保证安全；没有可验证的独占协调就只生成补丁，暂停覆盖和指针更新

有协调后主题已验证、STATE 写入超时：记录“主题已保存；STATE 结果未知；入口尚未推进”。先读取确认，不重复创建。如果确认 STATE 已保存而入口更新失败，只报告部分成功；下一次从最新入口与实际文件状态恢复，不能重新生成全套文档。

## 新会话恢复与离线

新执行者拿到 P1 入口：先读目标/阶段/状态，发现当前任务是检查错误恢复，不立即把 35 页规格与所有聊天塞进上下文；按 INDEX 打开错误码、兼容性和验收章节，查看 E10。提交修改前要读完整待改文件；执行所需的只读资料仍按主题分层。

若只有旧缓存：说明使用哪一版、哪些关键来源未确认。可以准备测试计划；不能宣称已经与云端同步，也不能在未知安全阻塞下发布。保留带 base_revision 的待应用补丁，联网后重读再合并。

## 讨论没定案：保存已知信息，同时询问

用户讨论了“统一单体”与“拆为两个服务”，最后说“各有好处，先记下来”。既有批准架构是单体；拆分会改变部署、排期和验收。

不能提炼成“已决定拆成两个服务”。先保存比较的最少依据和未决项 Q-07，保留旧批准架构，关联受影响的部署文档与 Linear 任务（若已绑定），然后问：

“服务拆分还没定案，会影响部署和验收。你希望选择 A：本期保留单体；B：批准本期拆分；还是 C：暂不决策？我的建议是先补部署成本对比，但这还不是已批准决定。”

在回答前可继续两方案共用的无关测试，暂停依赖新架构的实施。选 C 后记录 status: proposed + disposition: deferred，按已明确的现行批准范围工作；若用户没约定下次讨论时间，就只记需何种信息再讨论，不自行设期限或以沉默补成 A。已知进展与待决记录仍可在授权内同步，不能因尚未定案把整次保存丢弃。

对照：如果用户明确说“暂不决定，先存一下”，这已经选择暂缓。直接保存 status: proposed + disposition: deferred、影响范围和实际约定的重议条件；不要立即再问 A/B/C。只有新增阻塞、期限变化或新的重要证据使决定重新必要时再提出问题。
