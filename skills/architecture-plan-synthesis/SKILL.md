# Architecture plan synthesis

将“当前仓库 + 项目计划 + 本次目标”综合为可实施的架构设计和按依赖排序的开发路线图。现状必须有依据，方案必须有决策，任务必须能被工程师或 coding agent 独立执行和验收。

## 1. 建立当前基线

从用户提供的路径、仓库链接、计划链接或导出文件开始。读取适用的 `AGENTS.md`、相关架构和项目知识，再沿本次改动的入口、调用者、契约、存储、测试和 UI 查证。记录仓库分支/提交、工作区差异及计划快照时间；将未提交实现与主线状态分开。读取远程计划时使用可用连接器，检索相关里程碑、任务、依赖、验收与交付证据。

形成简短的证据对照：需求、现有实现、计划任务 ID/状态、差距、证据来源。用户的最新指令决定目标；源码和验证证据说明实现现状；任务平台说明计划与工作状态。遇到冲突，明确列出差异和建议，分别保留来源，不用单一来源覆盖另一来源。

既有 Done、任务 ID、已确认边界和验收记录作为基线保留；重新评估未完成工作。发现 Done 与代码证据不符时，提出核查项和影响，不静默重开、重编号或重写外部状态。明确区分“已实现”“本地检查通过”“真实集成验收通过”“拟议方案”。

历史讨论和 可用的历史检索工具 可帮助还原用户意图；其中的模型回答、候选排名和页面标题不是当前能力证明。只在用户提供或需要延续历史时检索相关记录，不要求每次使用本技能都安装历史工具。

## 2. 收敛关键决策

先确定目标、非目标、用户操作链路、系统边界、数据与执行所有者、兼容约束。解释建议选择及被放弃方案的具体代价，复用已存在的组件和真实适配边界。

外部 CLI/API、会话协议、平台限制或新依赖影响方案时，核对当前官方资料并引用日期/版本。评估成熟实现的维护、许可证、架构适配与替换成本；公开代码不等于可直接复用。无法证实的能力列为未知，安排有明确成功证据、失败条件和停止条件的探针，放在依赖它的承诺之前。规划探针不等于已执行探针。

缺失信息只在会改变边界、所有权、兼容承诺或交付可行性时提问。可独立推进的部分继续完成；其余采用标明影响和验证方式的假设。来源不可访问时说明范围与缺口，依据可读材料交付有界方案，不编造远程内容或实时状态。

## 3. 写出架构与执行路线图

起草前读取 [交付契约](references/deliverable-contract.md)，按项目规模使用其中的结构与任务卡。

架构说明从当前状态到目标状态的具体变化：责任边界、关键数据和接口契约、用户交互、正常/失败/恢复流程，以及实际涉及的安全、迁移和发布约束。为重要能力或决策分配稳定引用，沿用项目已有编号体系。

路线图把架构差距拆成可交付任务。每张任务卡写清目标、关联架构条目和既有任务、影响模块、输入输出、前置依赖、验收证据、风险与阻塞条件。已确认路径与拟新增路径分开标记。粒度以独立可实现、可验证为准；跨边界工作按契约、实现、集成和真实验收拆分。

根据前置条件排序，而非照抄旧计划或 UI 优先级。检查依赖缺失、自依赖和循环；说明解除冲突的建议，给出关键路径、可并行工作和阶段退出 Gate。没有资源与工期依据时只承诺依赖顺序，不虚构负责人、截止日期或精确耗时。

## 4. 核对并交付

检查每项范围内的架构能力都有实现/验证任务，每个任务都有设计依据；数据、契约、状态名称和依赖在各部分一致。由仓库配置推导验证命令，标明已执行结果或计划执行；无法确定时说明缺失依据。外部验收 Gate 与本地测试分别列出。

默认按用户语言保存一个完整的 `<project>-architecture-plan.md`，含架构与路线图，并提供真实文件链接。用户要求两份文档或其他格式时遵从，保持双向引用。文件功能不可用时输出完整 Markdown 内容并说明限制。聊天摘要不替代完整交付物。

本技能交付规划。仅当用户同时授权时才修改业务代码、同步 Linear/其他平台、发送消息或执行真实外部探针；已获授权的动作无需重复确认。同步时保留既有 ID/证据，读回结果，遇到结果未知先查询再重试。
